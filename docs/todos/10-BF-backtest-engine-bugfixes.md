# BF: Backtest Engine Bug Fixes (Entry/Exit/PnL/Risk/Analytics audit, 2026-08-14)

**See**: docs/todos/00-OVERVIEW.md for structure/anchors/maintenance conventions. This file tracks fixes for the defect list found by a manual + multi-agent audit of the backtest pipeline (entry, exit, PnL, risk, post-trade analytics) on 2026-08-14, `imgui` branch. Findings were cross-verified by direct code trace and an independent `/code-review high` multi-agent pass; every item below was confirmed against the actual source, not inferred from a code smell.

**Scope note**: the safe target designs for BF-01..BF-03, BF-07, BF-09, and BF-13..BF-17 touch the repository's Phase 1 frozen surface (docs/todos/02-P1-freeze.md). Those changes need the `LIVE_SAFETY_CCB_APPROVED` commit token, human ADR/CCB approval before implementation, human merge approval, and a clean multi-hour `engine_shadow` run per `docs/governance/02-prerequisites.md` before merge. Always use the checker as the authoritative path list. Because the BF-01/BF-02/BF-03/BF-09 plans below restate frozen safety behavior, their documentation changes are themselves freeze-adjacent and are not merge-ready without the same required review evidence.

**Root cause driving the highest-severity cluster (BF-13..17)**: closing/flip orders are attributed to their true opener only by inference (self-opener fallback in `engine::register_order_meta` when the order carries no explicit `opener_order_id`), not by an explicit, carried value. `ExitManager`, `portfolio::apply_lot_fill`, and `register_strategy_exit_intent` each make a different assumption about what that inferred id means, and they silently disagree the moment a fill both closes an old lot and opens a new one in the same event, or an order the engine itself synthesizes (unwind/flatten) never gets attributed at all. Fix the attribution once (BF-13) and BF-14/16/17 become straightforward call-site changes instead of three separate workarounds.

## Workstream A — Independent fixes (freeze exceptions called out per item)

Ordered by severity/live-risk, not by file.

- **BF-04 — RESOLVED (2026-08-16)** `union_mode` now preserves Strategy intents and appends at most one Platform intent containing exactly the globally missing configured SL/TP/trailing leg types. An empty Strategy plan keeps the complete Platform plan, and existing Strategy trails are no longer duplicated through the old SL-only branch. This fixes the policy merge only; it does not claim that every multi-intent leg is venue-resting. **Files**: `src/exits/default_exit_policy.{h,cpp}`. **Regressions**: the five `BacktestDefects.BF04_UnionMode*` tests in `tests/test_default_exit_policy.cpp`.

- **BF-05 — RESOLVED (2026-08-16)** MC now carries exact per-trial gross profit/loss and reports the economically meaningful pooled factor `Σtotal_win / Σtotal_loss`, sentinel-free valid-trial mean/median, explicit valid/unbounded coverage, and an unbounded-campaign flag. The existing `mc_aggregate_v1` mean/median keys retain their legacy all-trial semantics; all corrected metrics are additive and the text report uses them as the primary values. **Files**: `src/analytics/analytics.h`, `src/simulation/monte_carlo_{types,controller,reporter}.*`. **Regressions**: `TEST(BacktestDefects, BF05_McProfitFactorMetricsIsolateZeroLossSentinel)` and `BF05_PooledProfitFactorUnboundedPolicyIsExplicit`.

- **BF-06 — RESOLVED (2026-08-16)** `Analytics::on_event` now terminates `event_type::signal` with its own no-op `break`, so it cannot fall through into the `l2_snapshot_event` downcast. Current strategies do not publish `signal_event`, but event-log replay can still deserialize and forward one, so the compatibility path remains relevant. **File**: `src/analytics/analytics.cpp`. **Regressions**: `Analytics.BF06_RealSignalEventDoesNotReachL2Handler` exercises the real event under normal and sanitizer builds; `Analytics.BF06_SignalTagDoesNotFallThroughToL2Handler` uses a valid L2 dynamic type with a signal tag to provide deterministic RED/GREEN dispatch evidence plus a positive L2 control.

- **BF-07 — RESOLVED (2026-08-22)** `engine::report_run_summary` (`engine_pending.cpp:168-174`) — throughput division now uses `safe_elapsed_s = (elapsed_ms > 0 ? static_cast<double>(elapsed_ms) : 1.0) / 1000.0` avoiding division by zero (`inf events/second`) for sub-millisecond fast in-memory runs. **File**: `src/engine/engine_pending.cpp`. **Regression**: `TEST(BacktestDefects, BF07_ReportRunSummarySubMillisecondSafe)`.

- **BF-08 — RESOLVED (2026-08-16)** `Analytics::on_fill` now rejects non-positive and non-finite fill quantities before any counter, latency, slippage, attribution, cash, position, or trade mutation. This closes the `commission * (close_qty / filled_qty)` NaN-poisoning path while preserving every positive finite fill. **File**: `src/analytics/analytics.cpp`. **Regression**: `TEST(Analytics, BF08_InvalidFillQuantityDoesNotMutateState)`.

- **BF-10** Design a complete resumable checkpoint v2. V1 restore has been withdrawn and is now rejected before engine or portfolio mutation because the diagnostic V1 snapshot omits lots, open orders, `total_fills_`, `total_funding_pnl_`, strategy/risk/execution state, and deterministic replay state. Do not extend or migrate the V1 reader; specify a new bounded, integrity-checked, crash-safe format that round-trips all required state before enabling resume. **Files**: new v2 checkpoint implementation plus the relevant state owners; keep `src/engine/checkpoint.{h,cpp}` V1 writing diagnostic-only. **Test**: a future v2 must round-trip lots/counters/orders and reproduce the same continuation as an uninterrupted run.

- **BF-11 — RESOLVED (2026-08-16)** `LocalBookAdapter` now maintains an intrusive FIFO over the existing `resting_` nodes, so volume-capped same-price bar sweeps follow submission order without a second container allocation or sweep-time sort. Partial fills retain priority; explicit modifies move to the tail; every cancel/full-fill erase unlinks centrally. **File**: `src/execution/execution_adapter.h`. **Regressions**: `TEST(BacktestDefects, BF11_VolumeCappedSweepFillsInSubmitOrder)`, `BF11_ModifyMovesRestingOrderToFifoBack`, and `BF11_CancelUnlinksWithoutReorderingSurvivors`. The paired Debug benchmark showed no median regression (range-miss scans were 36–39% faster in that configuration; no Release/p99 claim).

- **BF-12 — RESOLVED (2026-08-16)** Both unreferenced `portfolio::can_afford` overloads were removed instead of preserving a symbol-blind, spot-only predicate that could not model shorts, flips, margin, reservations, or reduce-only exits. Pretrade admission remains owned by `IRiskCheck`/`RiskManager`; no production call site changed. **Files**: `src/execution/portfolio.{h,cpp}`, `tests/test_portfolio.cpp`.

- **BF-18 — RESOLVED (2026-08-22)** `Analytics::on_fill` now checks `is_same_physical_fill = (f.get_fill_id() != 0 && f.get_fill_id() == last_fill_id_seen_)` so that decomposed flip legs (`f_close` and `f_open` sharing the same physical fill ID) do not double-increment `total_fills_`, latency observation metrics, or duplicate slippage accounting (`total_slippage_`, `slippage_count_`). **Files**: `src/analytics/analytics.{h,cpp}`. **Regressions**: `TEST(Analytics, FlipFill_DoesNotDuplicateSlippageOrFillCount)` and `TEST(BacktestDefects, BF18_FlipFillDoesNotDuplicateSlippageOrFillCount)`.

- **BF-19 — RESOLVED (2026-08-22)** `Analytics::on_funding` now aggregates notional across all positions holding the funded symbol instead of breaking prematurely after the first matching strategy entry, allowing exact funding rate derivation and correct cash delta accounting for multi-strategy setups. **File**: `src/analytics/analytics.cpp`. **Regression**: `TEST(Analytics, MultiStrategy_FundingRateDerivation)`.

## Workstream B — Frozen-surface track (requires `LIVE_SAFETY_CCB_APPROVED` + CCB + clean shadow run)

BF-01 and BF-03 are separate close-order and venue-bracket lifecycle design tracks. BF-02 and BF-09 are one active-order lifecycle/capacity track. Within the attribution cluster, do BF-13 first — it is the shared foundation the other four build on. Land BF-13..BF-17 in one CCB cycle if scope allows; the freeze-process cost is per PR, not per bug, so batching avoids paying it five times for small diffs that all touch the same functions.

- **BF-01 — OPEN; LOCAL GUARD REJECTED AS LIVE-SAFETY FIX (2026-08-16)** The current worktree exempts orders inferred from the local net position as `reducing_exposure` from spread/funding breakers. That repairs the isolated `RiskManager` branch and correctly rejects a single order that crosses zero, but it is not a close-only guarantee and must not be certified or merged as the live fix. `order_event` carries no close-only flag; `RiskManager`/generic order admission does not reserve already-outstanding close quantity per symbol (`ExitManager` has only narrower per-opener in-flight accounting for its own triggered exits); Binance Futures ordinary orders omit `reduceOnly`; Bitget ordinary orders default to `"reduceOnly":"no"`; and local position can differ from the venue. Two GTC sells of 10 against one local long of 10 therefore both pass the snapshot check and can jointly open a short. The guard also suppresses the explicit severe (`halt`) branch for an inferred reduction, while the existing tests unrealistically ask the same manager to pass an exit after first returning `halt`; a live/shadow engine would already have latched its terminal halt. The safe design needs an engine-validated per-order close-only contract, per-symbol outstanding-close reservations through partial fill/cancel/reject, venue `reduceOnly`/equivalent enforcement or fail-closed refusal, reconciliation-aware ownership, and distinct moderate versus severe outcomes. Reservation and attribution must survive ambiguous post-write submit/cancel outcomes, late fills, and restart rehydration until an authoritative terminal result; amend/replace must update them atomically or refuse fail-closed. A severe breach must enter the approved halt/kill/flatten path without automatic retry while any close is admitted only under the proven close-only contract. The engine contract must keep halt write-once, reject every later normal order, and execute exactly the approved kill/flatten path. This crosses frozen event/engine/provider interfaces and requires a human-approved T3 ADR/CCB before implementation. Funding input remains dormant until its separate production wiring is completed. **Tests before implementation**: two concurrent full-size closes cannot flip; reservation follows partial fill/cancel/reject and ambiguous post-write outcomes; a late fill after cancel ambiguity cannot combine with another close to reverse exposure; restart restores venue-side close reservations before admission; amend/replace atomically re-reserves or refuses; each provider's payload enforces close-only or explicitly refuses the capability; venue/local divergence refuses; moderate close-only behavior is distinct from severe terminal halt; and the engine—not only `RiskManager`—proves write-once halt, no retry, no later normal admission, and exactly the approved kill/flatten sequence.

- **BF-02 — PARTIAL; FROZEN-LIFECYCLE BLOCKER (2026-08-16)** The old `total_orders - total_fills` capacity formula is gone, and the current worktree reserves a pending `OrderTracker` slot before queue/stop staging, keeps it through open/partial states, reuses it when a stop triggers, and releases it on the terminal transitions it actually receives. That is not yet an authoritative active-order capacity/reservation count. In the user-data path, `ExecutionBridge` consumes `parsed_exec::{canceled,rejected,expired}` for known order ids without emitting a tracker event; `LocalBookAdapter` supplies no terminal transition for IOC/FOK no-fill or IOC partial-rest cancellation; a delayed local cancel is counted terminal immediately although the adapter can still match the order; and unrestricted terminal-to-active transitions or unknown late ACKs can create phantom slots. Delegated/recovered venue brackets are not reserved before their first fill, and the unknown-bracket fill path currently mints a fresh engine id for every message, so a partial fill and later terminal fill for the same exchange order do not share a stable tracker lifecycle. Both `RiskManager::check_order` overloads also default a missing count to zero, silently bypassing the cap. Capacity admission currently happens only in `route_order`/`process_order`: the three risk workers consume the stamped count but ignore `risk_action::reject`, while their separately injected Atomic references are unused, so neither worker-side path currently enforces this limit. The event-stamped count is also absent from event-log serialization and therefore becomes zero on replay. A complete fix must define one engine-owned transition API/state machine, authoritative terminal events from every adapter/bridge path, stable tracker identity across all messages for one exchange order, conservative ambiguous-result/reset/restart handling, mandatory capacity input, and a bounded active store coordinated with BF-09. Its population contract must explicitly decide whether delegated venue brackets, recovered venue orders, and safety/unwind orders share this cap or require separately bounded reservations; coordinate that decision with BF-03. It must also choose whether replayed orders are risk-rechecked or carry a persisted admission snapshot, and either make worker rejection operational or remove the misleading worker count plumbing. The hot path needs one map lookup per transition and a measured/justified counter synchronization policy; the current second hash lookup, unused worker plumbing, current event-size increase, and potential p99 impact are not yet certified. The expected scope includes frozen `src/engine/engine.cpp`, `src/engine/engine.h`, `src/engine/engine_pending.cpp`, `src/risk/risk_manager.h`, and `src/execution/execution_bridge.h`, likely frozen `src/execution/async_support.h`, plus `src/execution/execution_adapter.h`, `src/core/event_log.h`, `src/core/event.h`, `src/risk/risk_manager.cpp`, `src/execution/order_tracker.h`, and the three risk-worker headers; a separate population cap may also require frozen `src/engine/engine_config.h`. The exact ADR-dependent scope therefore requires T3/CCB. **Tests before implementation**: `TEST(BacktestDefects, BF02_MaxOpenOrdersSurvivesMultiFillOrder)` with a deterministic old-code RED and a real three-level engine fill; a persistent partially filled GTC blocks a competitor until full fill or authoritative cancel; IOC/FOK zero- and partial-fill release; delayed cancel remains active until authoritative completion; venue canceled/rejected/expired transitions; multiple messages for one bracket `exchange_order_id` retain one tracker identity and the terminal message restores the prior count; no terminal-to-active or unknown/stale-ACK resurrection; pending stop competes for capacity and reuses exactly one slot; confirmed cancel/reject releases it; reset/restart/recovery is conservative; while both worker inputs exist, all three workers receive deliberately contradictory stamped versus Atomic counts to characterize priority and rejection, and after the design decision only the retained contract remains tested; `OrderTracker` covers Active-to-Rejected, Partial-to-Cancelled, and repeated terminal idempotence; event-log/replay semantics are explicit; if the Atomic contract remains, concurrent readers are phase-synchronized so the test cannot pass with zero observations; and before/after hotpath/p99 measurement.

- **BF-09 — OPEN; FROZEN-INTEGRATION BLOCKER CONFIRMED (2026-08-16)** `OrderTracker::statuses_` still retains one node per order for the full run, and `get_open_orders()` (test-only in-tree) scans that history. `active_count()` is O(1) in the current partial BF-02 worktree, but that implementation remains uncertified until the joint lifecycle design lands. Do not add header-only terminal eviction: unknown IDs currently read as `pending`, so erasure can reopen a terminal order through a late submit ACK; conversely, a global ID watermark can suppress a legitimate first partial fill for an asynchronously synthesized venue-bracket leg that has not previously entered the tracker. The safe design is an active-only, fixed-capacity tracker with explicit `begin`, `transition_existing`, and `finish_existing` operations, engine-visible exhaustion handling, and complete lifecycle emission to the configured `IOrderAuditSink`; only a persistent sink owns durable storage, while `NoopOrderAuditSink` intentionally retains no lifecycle history. That requires coordinated frozen lifecycle call-site changes in `engine.cpp`/`engine.h` (and likely capacity config), so it needs the T3/CCB track. `engine::order_meta_` is a separate unbounded lifecycle map and must be addressed in the same memory-bound design, coordinated with BF-13. **Tests**: separately bound both Tracker storage and `order_meta_` during long-run churn and prove metadata release after authoritative terminal state; prove zero-allocation after prewarm and loud capacity exhaustion; terminalize higher ids, then accept a previously unseen lower synthetic bracket id as a partial fill and release it cleanly on terminal completion; prove that a late ACK cannot resurrect a terminal order; prove that a released capacity slot is reusable; and use a recording/spy sink to prove every lifecycle transition is emitted before active-store release and any diagnostic-cache eviction, while keeping the Noop sink explicitly non-durable.

- **BF-03 — OPEN; DELETE-ONLY FIX REJECTED (2026-08-16)** `ExitManager::on_price` / `on_bar` intentionally cancel the opener-wide venue bracket before routing an engine-side partial exit. Do not delete that unconditional release while siblings remain: only one unordered `to_place.front()` intent is delegated, while `handles_` records no intent identity, placed quantity, or sizing mode. The retained venue order could therefore belong to the leg that just fired or carry a stale fixed quantity; a later fill can duplicate the close and even reverse a netted position. Keep the conservative cancel-before-route behavior until the model has stable intent IDs, explicit handle-to-intent ownership, placed-quantity and fixed-quantity versus reduce-only/full-position capabilities, cancel-pending attribution that survives late fills, and a confirmed cancel/replace path for the exact residual exposure. The redesign must also make trigger-state mutation transactional: today quantity, armed intent, and in-flight reservation are mutated before a throwing venue cancel prevents the local close from being returned. Its frozen scope includes provider adapters plus `engine.cpp`, `async_support.h`, and `execution_bridge.h` in the fill-attribution path; `recovered_bracket` must round-trip intent identity and sizing mode. Certify every adapter in a capability matrix, including an enforced partial-intent policy, and correct the stale generic claim that a duplicate close at flat is harmless. For ambiguous cancel or replacement failure, halt without automatic retry, retain reverse attribution, and do not emit a competing local close until the venue outcome is authoritative; if a venue fill wins the race, attribute that fill to its exact leg and suppress the duplicate local close. Retain the mapping through an authoritative terminal outcome: confirmed cancel or fully processed terminal fill; a partial fill retains attribution until its remainder is resolved. Only then may residual cancel/replace or local close routing proceed. These semantics require a human-approved T3 ADR/CCB before implementation; there is no complete live-safe two-line fix in `exit_manager.cpp`. **Tests before implementation**: cover both `on_price` and `on_bar`, delegated and non-delegated siblings, stale fixed-quantity over-close, later opener partial fills, cancel-confirmed/cancel-ambiguous/venue-fill-wins/replacement-fails interleavings, deterministic ownership, restart rehydration, flat/full release, and per-adapter sizing contracts.

- **BF-13 — RESOLVED (2026-08-21)** (root-cause) Introduced same-fill flip decomposition in `FillProcessor::handle_fill`: when a single fill reverses an opposing position (`fill_qty > |pos.qty|`), it is split into two distinct attributed legs prior to downstream dispatch: a close leg for the exact opposing quantity referencing the prior lot opener ID, and an open leg for the residual quantity referencing the new order ID. This cleanly isolates lot closures, bracket cancellations, realized PnL in Analytics, and arms pending exit intents for the net-new exposure. **Files**: `src/engine/fill_processor.cpp`, `src/engine/engine.h`. **Regression**: `TEST(BacktestDefects, BF13_SameFillFlipAttributesCloseAndOpenSeparately)` in `tests/test_backtest_defect_engine_loop.cpp`.

- **BF-14 — RESOLVED (2026-08-21)** `OrderIntentProcessor::unwind_positions`: closes each open lot individually (`portfolio_.get_lots()`) with the true `opener_order_id` and sentinel strategy name stamped on each closing order, followed by closing any residual unlotted position. Ensures all armed brackets for multi-lot positions are cleanly cancelled/disarmed on operator flatten or risk-unwind. **Files**: `src/engine/order_intent_processor.cpp`, `src/engine/engine.cpp`. **Regression**: `TEST(BacktestDefects, BF14_UnwindMultiLotPositionClearsAllBrackets)`.

- **BF-15 — RESOLVED (2026-08-21)** `FillProcessor::dispatch_fill_to_strategy`: checks for distinguishable unwind sentinels (`strategy_name == "__engine_unwind__"` or `"risk_unwind"`) and skips delivering unwind/flatten fills to the primary strategy's `on_fill()`. **Files**: `src/engine/fill_processor.cpp`, `src/engine/order_intent_processor.cpp`. **Regression**: `TEST(BacktestDefects, BF15_UnwindFillNotDeliveredToStrategyOnFill)`.

- **BF-16 — RESOLVED (2026-08-21)** `OrderIntentProcessor::finalize_route` / `register_strategy_exit_intent`: captures `pre_route_net_qty` before `route()` is invoked and threads it through to `register_strategy_exit_intent`, so synchronous signal-closing fills are accurately evaluated as position-reducing and do not spuriously arm inverted brackets on flat positions. **Files**: `src/engine/order_intent_processor.h`, `src/engine/order_intent_processor.cpp`, `src/engine/engine.cpp`, `src/engine/engine_market.cpp`. **Regression**: `TEST(BacktestDefects, BF16_SyncFillClosingOrderDoesNotArmInvertedBracket)`.

- **BF-17 — RESOLVED (2026-08-21)** `portfolio::apply_lot_fill`: hardened defensive clamping (`std::clamp(fill_qty, 0.0, max(0.0, qty_open))`) ensuring open lot quantities never go negative or leave orphaned lots. **Files**: `src/execution/portfolio.cpp`. **Regression**: `TEST(BacktestDefects, BF17_FlipFillLeavesNoOrphanedOldLot)`.

## Open questions to resolve before implementing

- **BF-01**: define which order source may assert close-only, how the engine reserves/reconciles that quantity, and how each venue proves enforcement. The ADR must separate admission of a proven close-only order from the terminal response to a severe breaker; a local net-position inference alone authorizes neither.
- **BF-02**: define the canonical status machine and which component authoritatively emits each submit/open/partial/filled/canceled/rejected/expired transition. Define whether delegated venue brackets, recovered venue orders, and safety/unwind orders consume the same reservation population or a separately bounded one. Decide whether workers consume a persisted admission snapshot or a live count, make their rejection operational or remove that misleading contract, and make replay/reset/recovery semantics explicit before changing the frozen interfaces.
- **BF-03**: define a generic, falsifiable venue-bracket sizing contract before choosing retention versus cancel/replace. A handle's exact delegated intent, nominal quantity, sizing mode, lifecycle, and late-fill attribution must remain known through cancel completion and restart recovery; a surviving engine-side sibling is not evidence that the existing venue order protects that sibling. The ADR must enumerate the state of mappings, armed siblings, remaining/in-flight quantity, local-close emission, and terminal halt for every cancel-confirmed, cancel-ambiguous, venue-fill-wins, and replacement-fails interleaving.
- **BF-09**: full-run Tracker history has no in-tree consumer. The engine must emit every lifecycle transition before releasing active state; durable history exists only when a persistent audit sink is configured, while `NoopOrderAuditSink` retains no lifecycle history apart from its rejection counter. Decide whether this emission-only contract is sufficient; requiring every sink to retain history would add `src/engine/order_audit_sink.{h,cpp}` to the design scope. The remaining decision is the CCB-approved hard active capacity and fail-closed exhaustion contract. A recent-terminal cache may be diagnostic only; it cannot substitute for explicit begin/transition/finish lifecycle APIs.
- **BF-10**: define the v2 compatibility and migration contract before implementation. Existing V1 files are diagnostic-only inputs, not resumable migration sources.
- **BF-13**: confirm no other internal caller besides `unwind_positions` and organic strategy flips currently relies on the self-opener fallback in a way that would break if it's narrowed — grep all `route_order`/`process_order` call sites for orders that never set `opener_order_id` on purpose, before changing the default.
