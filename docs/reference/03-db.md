# QuestDB Persistence (Authoritative Reference)

**Note**: docs/ is now the central authoritative documentation home. Last updated: 2026-07 (docs overhaul). Branch context note removed as obsolete.

**Golden rule**:
> The **binary zstd event log** (`--record`) is the mandatory, durable source of truth for every session.  
> QuestDB (`--persist`) is the high-performance, SQL-queryable secondary store for analysis, dashboards, and operational visibility.

## Current Tables (as implemented in `src/data/questdb/schema.cpp`)

### Shared Table

```sql
CREATE TABLE IF NOT EXISTS runs_meta (
    run_tag          SYMBOL CAPACITY 10000 INDEX,
    started_at       TIMESTAMP,
    ended_at         TIMESTAMP,
    mode             SYMBOL CAPACITY 4,           -- backtest | shadow | live
    binary           SYMBOL CAPACITY 4,           -- engine_backtest | ...
    strategy         SYMBOL CAPACITY 64,
    symbol           SYMBOL CAPACITY 1024,
    params           STRING,
    initial_equity   DOUBLE,
    final_equity     DOUBLE,
    total_orders     LONG,
    total_fills      LONG,
    total_rejections LONG,
    notes            STRING
) TIMESTAMP(started_at) PARTITION BY MONTH;
```

### Per-Run Tables (namespaced by `run_tag`)

All use `PARTITION BY DAY` + designated `TIMESTAMP` column.

- `{run_tag}_orders`
- `{run_tag}_order_status`
- `{run_tag}_fills`
- `{run_tag}_rejections`
- `{run_tag}_cancellations`
- `{run_tag}_amendments`
- `{run_tag}_events` (Phase 3: generic decision/logic events with event_type, severity, message, details JSON)

## Connection & Protocol

- **DDL / metadata**: HTTP on port 9000 (`/exec?query=...`)
- **Ingestion**: ILP (InfluxDB Line Protocol) on port 9009 (persistent TCP connection with buffering + reconnect)
- Implementation: `QuestdbStore`, `IlpWriter`, `TcpClient`, `HttpClient` under `src/data/questdb/`

---

## Current Reliability Model

- **Soft-fail by default**: If QuestDB is unreachable at session start, the engine continues without persistence. No data is lost from the binary log.
- **Time-based flushing (Phase 1 complete)**: `QuestdbStore::tick()` is now called periodically (~150 ms default, configurable via `--questdb-flush-ms`) from all major run loops. This greatly reduces the risk of losing buffered rows during long quiet periods or on crash.
- ILP writer provides `pending_lines()`, `dropped_lines()`, connection state, and last successful flush time.
- No local fallback on persistent write failure yet.
- `--persist-strict` (hard-fail + local ILP fallback file) is planned for Phase 2.

## Retention & Long-Run Operational Polish (Phase 4)

### Partitioning Strategy
- Per-run tables (`*_orders`, `*_fills`, `*_events`, etc.) use `PARTITION BY DAY` — excellent for 30-90+ day campaigns.
- `runs_meta` now uses `PARTITION BY WEEK` (changed from MONTH in Phase 4) for better query pruning on long-running or many-campaign use cases.

### Retention / TTL Recommendations
QuestDB does not support efficient row-level deletes. Use partition-level retention:

```sql
-- Example: keep only last 90 days of a long campaign
ALTER TABLE run_2026xxxx_events DROP PARTITION WHERE ts < dateadd('d', -90, now());

-- Or set TTL at table creation time (recommended for new long runs)
CREATE TABLE ... PARTITION BY DAY TTL 90 DAYS;
```

See the hardening guide for automated strategies using Enterprise Storage Policies.

### Golden Queries for Long Campaigns

**Reconciliation between binary log and QuestDB (critical for evidence):**
```sql
-- Compare order counts
SELECT 
    'QuestDB' as source,
    COUNT(*) as order_count
FROM run_2026xxxx_orders
UNION ALL
SELECT 'BinaryLog', ... ;  -- populated via external analysis of .ttlog.zst
```

**Campaign performance summary (uses Phase 4 richer runs_meta):**
```sql
SELECT 
    run_tag,
    strategy,
    final_equity - initial_equity as pnl,
    max_drawdown,
    sharpe_ratio,
    profit_factor,
    win_rate,
    (ended_at - started_at) / 1_000_000_000.0 / 86400 as duration_days
FROM runs_meta
WHERE ended_at IS NOT NULL
ORDER BY started_at DESC;
```

**Detect sessions with fallback data (from Phase 2):**
```sql
SELECT run_tag, COUNT(*) as fallback_events
FROM run_2026xxxx_events
WHERE event_type = 'fallback_written'
GROUP BY run_tag;
```

## Build & Runtime

- CMake: `-DENABLE_QUESTDB=ON` (uses raw POSIX sockets — zero extra runtime dependencies).
- CLI: `--persist --run-tag myrun_... [--questdb-host ...] [--persist-strict]`
- Config file and JSON also supported.

## Run Tag Rules (enforced early)

- Max length: 64 characters
- Allowed characters: `[A-Za-z0-9_]`
- Must be non-empty
- Invalid tags throw at `--run-tag` parsing time (before any DB work)

See `src/data/questdb/run_tag.cpp` for the validator.
