# QuestDB Persistence (Authoritative Reference)

**Note**: `docs/` is the central documentation home. Last updated: 2026-08-14 from `src/data/questdb/schema.cpp`, `src/bin/main.inc`, and `QuestdbStore`.

**Golden rule**:
> The **binary zstd event log** (`--log-events <path>`) is the durable audit source.
> QuestDB (`--persist`) is the high-performance, SQL-queryable secondary store for analysis, dashboards, and operational visibility.

`--record <path>` is different: it records raw market-transport messages and is not the binary engine event log.

## Connection & Protocol

- **DDL / metadata**: HTTP on port 9000 (`/exec?query=...`)
- **Ingestion**: ILP (InfluxDB Line Protocol) on port 9009 (persistent TCP connection with buffering + reconnect)
- Implementation: `QuestdbStore`, `IlpWriter`, `TcpClient`, `HttpClient` under `src/data/questdb/`
- **HTTP framing / bounds**: `/exec` accepts only HTTP/1.0 or HTTP/1.1
  responses with exactly one valid `Content-Length`; chunked, close-delimited,
  duplicate, malformed, oversized, and truncated responses fail closed. The
  hard limits are 64 KiB for headers, 1 MiB for bodies, and 64 KiB for the SQL
  request; embedded C++ callers may make response limits stricter, never
  weaker. One absolute deadline covers all socket connect/write/read phases
  and resolved address candidates. Synchronous platform DNS resolution remains
  outside that deadline, so strict callers should use numeric or pre-resolved
  QuestDB hosts.

## Current Reliability Model

- **Soft-fail by default**: If QuestDB is unreachable at session start, the engine continues without persistence. No data is lost from the binary log.
- **Time-based flushing**: headless run loops call `QuestdbStore::tick()` from
  their roughly 200-ms reporting cadence. `--questdb-flush-ms` is therefore a
  writer-side minimum, not a guarantee of a shorter end-to-end interval.
  Dashboard streaming avoids synchronous timer-driven network I/O on the
  market callback; threshold flushes and finalization still apply, and strict
  write failures signal the engine immediately.
- The ILP writer bounds retained payload to 4 MiB by default
  (`StoreConfig::max_pending_bytes` for embedded C++ callers). It provides
  `pending_lines()`, `pending_bytes()`, `dropped_lines()`, connection state,
  and last successful flush time. Under pressure it preserves the oldest FIFO
  batch, tries an already-connected transport or a configured fallback, then
  rejects and counts only newer lines if space remains unavailable. An
  oversized individual line is rejected rather than growing the retained
  buffer; a zero cap deliberately rejects every line.
- When configured, the local fallback file receives the pending ILP batch only
  after a pre-send transport failure (no batch bytes accepted locally). A
  partial/ambiguous TCP write is quarantined in memory: it is neither retried
  nor written to the fallback automatically, and must be reconciled against
  the binary event log. A fallback write/flush error is itself latched; the
  buffer is retained and is never counted as persisted. The fallback is
  diagnostic and does not convert a strict persistence failure into success.
- `--persist-strict` is implemented for normal engine runs: startup or runtime ILP/QuestDB failure produces a non-zero result; shadow/live also latch terminal halt. Monte Carlo rejects this flag until its separate summary writer can honor the same contract. The fallback file is diagnostic and does not turn a failed strict write into success.

## Retention & Long-Run Operational Polish (Phase 4)

### Partitioning Strategy
- Per-run tables (`*_orders`, `*_fills`, `*_events`, etc.) use `PARTITION BY DAY` — excellent for 30-90+ day campaigns.
- `runs_meta` now uses `PARTITION BY WEEK` (changed from MONTH in Phase 4) for better query pruning on long-running or many-campaign use cases.

### Retention / TTL Recommendations
QuestDB does not support efficient row-level deletes. Use partition-level retention:

```sql
-- Example: keep only last 90 days of a long campaign
ALTER TABLE run_2026xxxx_events DROP PARTITION WHERE ts < dateadd('d', -90, now());

-- Or set TTL at table creation time (recommended for new long runs)
CREATE TABLE ... PARTITION BY DAY TTL 90 DAYS;
```

See the hardening guide for automated strategies using Enterprise Storage Policies.

### Golden Queries for Long Campaigns

**Reconciliation between binary log and QuestDB (critical for evidence):**
```sql
-- Compare order counts
SELECT 
    'QuestDB' as source,
    COUNT(*) as order_count
FROM run_2026xxxx_orders
UNION ALL
SELECT 'BinaryLog', ... ;  -- populated via external analysis of .ttlog.zst
```

**Campaign performance summary (uses Phase 4 richer runs_meta):**
```sql
SELECT 
    run_tag,
    strategy,
    final_equity - initial_equity as pnl,
    max_drawdown,
    sharpe_ratio,
    profit_factor,
    win_rate,
    (ended_at - started_at) / 1_000_000_000.0 / 86400 as duration_days
FROM runs_meta
WHERE ended_at IS NOT NULL
ORDER BY started_at DESC;
```

Fallback rows live in the local `.ilp` fallback file, not in a synthetic QuestDB `fallback_written` event. Archive and reconcile that file with the binary event log before treating a run as complete.

## Build & Runtime

- CMake: `-DENABLE_QUESTDB=ON` (uses raw POSIX sockets — zero extra runtime dependencies).
- CLI: `--persist --run-tag myrun_... [--questdb-host ...] [--persist-strict]`
- Config file and JSON also supported.

## Run Tag Rules (enforced early)

- Max length: 64 characters
- Allowed characters: `[A-Za-z0-9_]`
- Must be non-empty
- Invalid tags throw at `--run-tag` parsing time (before any DB work)
